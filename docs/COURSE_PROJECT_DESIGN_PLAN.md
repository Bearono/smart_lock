# 智能门锁与摄像头综合设计：调研比较与实施方案 v2

日期：2026-10-08。面向电子科技大学大三上软件工程网络安全方向综合设计。

状态：推荐方案已选定；这是设计与实施计划，不代表下述新增能力已经实现。本轮不修改应用代码、部署或数据库。

## 1. 最终方向

采用 **温暖的家门使用界面 + 清楚的管理与安全证据界面**，两者共享一套组件、权限、领域状态和真实数据。

日常用户进入应用，应立即知道门锁最近状态、能否查看门前画面、如何验证并开门、如何邀请访客。答辩时，团队可以用管理员页面、隔离测试报告和协议流程解释同一次操作背后的身份验证、设备授权、消息完整性、防重放、命令有效期及执行反馈。

主界面采用燕麦白、暖灰、深陶土色主动作和少量柔和绿；不再以深色管理侧栏和设备统计建立首页。安全能力依靠真实机制和证据表现，不靠全屏代码、盾牌、虚构攻击计数或安全评分表现。

建议课题表述：**面向智能家居的多因素认证与安全通信门锁摄像头系统设计与实现**。这是题目建议，实际名称须遵循课程任务书。

## 2. 学校背景、方法与边界

学校的 [软件工程专业公开介绍](https://zs.uestc.edu.cn/view/1961.html) 强调软硬结合、系统性、网络安全训练及进阶式挑战性综合项目；[教学实践介绍](https://www.news.uestc.edu.cn/?Id=74242&n=UestcNews.Front.DocumentV2.ArticlePage) 说明项目驱动和过程能力的培养思路。这支持本方案重视完整链路和工程证据，但公开资料不是你们当前课程的评分表。

用户已明确暂不依赖任务书，确认硬件是 Raspberry Pi 4B / 2 GB。截止时间、团队人数、摄像头型号与锁具反馈方式尚未明确。按现有 Vue 前端、Flask 后端、树莓派设备软件、摄像头与门锁场景设计；硬件集成单独设置验收门槛，不因页面完成而宣称硬件验收完成。

本轮累计比较 16 个品牌/生态，新增 Eve、Homey、Arlo、Reolink；另比较 IoT 安全基线、Web 验证、设备测试、认证与安全开发框架。证据以官方产品页、支持文档、官方标准与项目源码为主。

局限：未在所有产品 App 中登录实测；营销截图不能证明版本一致或安全实现；颜色和结构建议是本项目设计判断；尚无真实家庭用户调研或满意度实验。旧报告 `WARM_HOME_DESIGN_RESEARCH.md` 作为上一轮材料保留，本文件是加入课程定位后的主方案。

## 4. 三类总体方案比较

以下是针对本项目的设计判断，不是市场测评或老师评分。

| 方案 | 家庭体验 | 网络安全成果展示 | 工程复杂度 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 完全消费级家居 App | 易于日常使用 | 深层机制不易被观察 | 中 | 答辩时容易只看到操作和配色 | 保留体验思路，补足证据入口 |

## 6. 功能范围与优先级

### 6.1 必须完整交付（P0）

- 登录、首次认证器绑定、会话失效与密码修改。
- 授权设备选择、最近锁状态、连接状态、摄像头状态、最近画面。
- 人脸结果/认证步骤、必要 TOTP、短期授权消费、命令反馈与未知结果恢复。
- 访客创建、次数与期限说明、验证、撤销；公共访客页。
- 动态记录、管理员审批和设备授权、真实报警处理。
- 暖色设计系统、手机和桌面布局、全套空/错/离线状态。
- 课程文档、隔离安全用例、可重复部署和答辩证据。

### 6.2 本轮完整扩展（P1）

- 后端持久化设备显示名称，使界面可以真实显示“入户门”。原 ID 留在技术详情。
- 明确时间契约；给快照提供可信的服务器接收时间，若设备采集时间可信则分别提供。
- 加强可追踪事件元数据，使新记录可以关联设备、请求/命令及结果。
- 只读安全证据入口，展示配置事实、真实业务链路详情与隔离测试报告。
- 管理设置与安全信息重新组织，日常页面只露出必要提示。

P1 包含数据、权限、迁移、接口、测试和文档，不能只添加前端假字段。实施时如任务书约束更严，可在冻结前明确调整范围。

### 6.3 暂不纳入基础交付（P2）

完整多家庭/多租户、通用自动化编辑器、云订阅、双向通话、直播录像、AI 事件摘要、模型训练平台、完整 OTA、Kubernetes、微服务拆分、原生 App、Passkey 迁移。

这些是独立产品能力，价值不等于越多越好。若老师明确要求实时视频、活体或实体开锁，应升级为独立必做任务，重新估计设备与安全工程范围。

## 7. 角色与信息架构

现有真实角色：管理员、普通已授权用户、持访客凭证的人。设备运行进程与运维者是另外两类系统参与者。暂不把普通用户擅自改造成拥有家庭模型权限的“家主”。

| 入口 | 普通用户 | 管理员 | 访客 |
| --- | --- | --- | --- |
| 我的家/设备详情 | 仅授权设备 | 依现有后端权限 | 无 |
| 最近画面 | 仅授权设备媒体 | 依明确策略 | 默认无 |
| 动态 | 原有权限范围内 | 审计范围内 | 无 |
| 邀请访客 | 符合绑定与授权前提 | 同一业务规则 | 使用本人凭证 |
| 账号与设备绑定 | 本人 | 本人及已有管理能力 | 无 |
| 审批/设备授权/报警处理 | 无 | 有 | 无 |
| 安全证据与验证报告 | 本人的必要信息 | 脱敏管理证据 | 无 |

后端是授权依据。导航隐藏、前端角色变量与路由守卫仅帮助交互，不作为安全边界。

手机底部四项：我的家、动态、访客、设置。管理员在设置中进入账号审批、访问授权、报警和安全证据；首页对其可见的未处理报警提供明显入口。桌面使用浅色导航和相同名称。保留旧路由兼容或明确重定向，不留下深链接断裂。

## 8. 每个页面的详细设计

### 8.1 我的家

桌面内容最大宽度建议 1200–1280 px；主区约 60% 画面、40% 门锁与动作。手机单列，画面、状态和主要操作连续排列，不在首屏塞三块设备统计。

内容顺序：简短欢迎与设备选择 → 重要异常 → 家门主区 → 邀请访客/动态快捷入口 → 最近动态。单台设备默认进入详情，多台设备增加轻量选择卡片。

主要操作：“验证并开门”“上锁”“获取最近画面”。进行中的结果在跨页面导航时仍可找到；手机固定提示区与底部导航预留安全间距。

标题使用真实显示名；无名称时回退 ID。锁状态未知显示“状态暂未确认”，并显示上次上报信息；设备在线只证明连接新鲜，不能证明门已锁或全家安全。

### 8.2 门前画面

当前模式是快照。标签写“最近画面”，图片本色展示，可放大；没有画面时显示明确占位和下一步。删除、无权限、故障和加载状态各自清楚。

新增时间先提供服务器收到画面的时间，不能将数据库入库时间宣称为设备拍摄时间。设备采集时间另加来源与可信度，设备时钟不可信时不生成“实时”提示。

不在无视频接口时展示直播绿点、假播放控件、录像拖动或对讲按钮。隐私说明围绕实际媒体访问权限与删除能力，不能写没有实现的端到端加密或设备隐私模式。

### 8.3 开门与上锁步骤

确认设备 → 获取人脸结果/完成所需认证 → 签发短期授权 → 提交命令 → 查询原命令 → 展示执行结果。具体认证条件依现有后端策略，不擅自改成所有动作都使用同一认证强度。

四类状态分别表达：身份验证状态、授权受理状态、命令执行状态、设备物理状态。操作成功提示依据对应证据；历史上报不覆盖本次命令，命令目标不充当传感器反馈。

消费响应丢失时恢复原操作，不重新签发并消费新授权；未知结果不自动重发。按钮和验证步骤保持清楚，在高风险转换处确认，不增加无意义的三连确认。

### 8.4 动态

日期分组、简短动作、人物/账号、来源、结果、必要缩略图。详情保留技术 ID 与原动作码。管理员可进入完整审计表。

当前开门控制记录缺少设备与命令关联，不能前端假合并成完整跨源时间线。本轮先用分区卡片保留已有分页；P1 新事件契约就绪后，才增加跨类型筛选、稳定排序和明确游标。旧记录标为“历史记录，设备信息未记录”。

### 8.5 访客与公共验证页

邀请表单：访客称呼、目标设备、有效时长、验证次数；预览真实规则后创建。卡片显示剩余额度、有效期、状态、分享和撤销。确认撤销说明影响原凭证和待执行权限。

当前支持 `guest_name`；保留并改善它。次数按接口的验证额度含义呈现，不叫成可保证成功的开门次数。

访客页只显示完成本次通行所需内容；凭证失效、响应不确定、执行失败都有独立提示。分享不把主账号令牌、认证器密钥或家庭媒体带给访客；凭证出现在 URL 时须专门审查日志和历史泄漏，优先不放查询参数。

### 8.6 设置与管理

普通用户：账号安全、认证器、已绑定设备、隐私与帮助。管理员增加账号审批、访问权限、报警处理和安全证据。

账号与访问权限采用卡片/分组设置，批量权限可继续使用清楚的表格；不为了圆角卡片牺牲权限矩阵可读性。改密、撤权、解绑后的旧会话与待执行授权继续遵循后端失效策略。

### 8.7 登录与初次设置

暖白底、小幅原创玄关插画、简洁表单，欢迎语言自然。认证器采用步骤式引导，安全要求讲清楚。没有默认生产密码，不公开真实设备口令。注册后的审批状态真实表达。

无设备时依据账号状态引导：审批 → 授权 → 绑定 → 等待设备上报。只有运维 CLI 才支持的功能不能伪装成已可点击的网页配对。

## 9. 视觉系统定稿原则

沿用上一轮 A 方向并收敛：燕麦白背景 `#F7F3EC`、暖白卡片 `#FFFCF7`、深暖灰正文 `#302D28`、深陶土主动作 `#985638`、温灰辅助 `#716A61`。正常 `#356B54`、提醒 `#886014`、危险 `#B33E3B` 保持独立语义。

关键色对已按相对亮度公式计算；真实页面仍需逐状态测量。正文默认 16 px，辅助 13–14 px，手机标题 24–28 px，桌面 28–32 px；主要卡片圆角 20–24 px，控件 10–14 px；触摸目标以 44×44 CSS px 为产品目标。

影像、人物和文字是主角；装饰仅用于登录、引导和空状态。真实摄像头画面不调色；演示图片明显标注。圆润图标使用一致笔画，不用 emoji 替代状态图标。动效仅帮助理解加载与步骤，尊重减少动态偏好。

无设备、离线和执行未知也需要达到同样的视觉完成度。正式设计稿必须覆盖这些状态，而不是只画理想状态。

可访问性依据 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)，触摸目标说明依据 [2.5.8 官方解释](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。44 px 是我们的更高产品目标，并非对 AA 规范最小值的错误引用。

## 10. 网络安全设计与可见证据

参考边界：

- [NISTIR 8259A](https://csrc.nist.gov/pubs/ir/8259/a/final)：用设备身份、配置、数据保护、接口访问、更新和状态感知审查能力完整性。
- [ETSI EN 303 645 V3.1.3](https://www.etsi.org/deliver/etsi_en/303600_303699/303645/03.01.03_60/en_303645v030103p.pdf)：参考默认凭据、敏感参数、通信、攻击面、断网恢复与用户数据处理等基线。
- [OWASP ASVS](https://owasp.org/projects/asvs)：用于选择 Web 安全要求；记录使用版本和具体要求，不宣称全级别合规。
- [OWASP ISTG](https://owasp.github.io/www-project-iot-security-testing-guide/) 与 [WSTG](https://owasp.org/www-project-web-security-testing-guide/)：设备与 Web 分开制定测试范围；ISTG 不能代替全部后端测试。
- [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final)：用于组织需求、开发、测试与发布证据。
- [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)：审查认证表述；TOTP 不是抗钓鱼认证，不能将当前多因素认证宣传成抵御全部身份攻击。

以上是设计与测试参考，不是合规认证结论。

### 10.1 威胁模型

明确边界：浏览器 ↔ Web 入口/后端；后端 ↔ 数据库与媒体；后端 ↔ 设备；设备 ↔ 摄像头、模板和执行驱动。攻击者包括未登录访问者、已登录但未授权的账号、持失效访客凭证的人、捕获或篡改设备消息的人；服务器/设备被完全控制及机械绕过另列限制。

| 威胁 | 安全要求 | 验证场景 | 允许展示的证据 |
| --- | --- | --- | --- |
| 越权开门或读图 | 服务端设备与对象授权 | A 用户尝试访问 B 设备或媒体 | 被拒结果、用例编号、脱敏关联记录 |
| 凭证重复消费 | 原子消费与并发约束 | 同一短期授权并发提交 | 单一命令产生，其余请求被拒 |
| 设备报文篡改 | 完整性认证与请求绑定 | 修改字段/密文/回执来源 | 校验失败，未改变业务状态 |
| 旧消息重放 | 持久化请求去重与时间边界 | 同包重复、并发、进程重启后重放 | 拒绝结果与去重测试记录 |
| 撤权后继续控制 | 生命周期失效与执行前复核 | 签发后撤权、访客撤销再执行 | 原授权和待执行操作失效 |
| 网络响应丢失 | 原操作可恢复且不自动重复动作 | 消费成功但响应丢失 | 同一命令查询恢复 |
| 虚假成功 | 执行回执校验和物理反馈区分 | 无驱动、失败、反馈不符、无回执 | 失败或未知，不显示已开门 |
| 认证尝试滥用 | 限流、挑战期限和失败处理 | 错误 TOTP、过期挑战、短期密集请求 | 规则触发与正常用户恢复路径 |
| 家庭影像泄漏 | 媒体鉴权、脱敏与最小存储 | 无登录读图、撤权后读图、缓存审查 | 权限测试和生命周期记录 |

现有源码包含 SPAKE2、HKDF、AES-CBC + HMAC、请求去重、短期命令及 TOTP 等机制。本轮不为展示效果更换密码协议。需审查身份/上下文绑定、失败路径、加解密顺序、并发和会话生命周期，不能因为库名或算法名就断言协议安全。

### 10.2 安全证据入口

管理员可看三个区域：配置事实、业务链路详情、隔离验证报告。配置事实如是否绑定认证器、角色与设备授权；没有遥测的内容显示“未提供”，不能猜测在线加密连接或攻击防护已通过。

一次业务链路可呈现请求、身份验证、授权、命令提交与执行结果，前提是对应元数据真实存在且权限正确。低层 MAC 校验不强行塞入每次人类开门流程，协议测试证据独立列出。

验证报告标识 Git 提交、环境、测试时间、用例、预期/实际、通过/失败/未运行。它证明那次测试的结果，不代表生产系统实时保证。报告在 CI/本机隔离测试运行，网页只读，不开放命令执行、任意 URL 请求或自由报文注入。

报告与页面不得输出设备口令、会话密钥、JWT、访客完整凭证、认证器种子、密文原文或个人脸图。算法流程静态图明确标为设计说明，不能伪装成实时观察。

### 10.3 现有缺口的处理

当前浏览器令牌在 localStorage，必须记录其 XSS 泄漏风险；先审查输出、第三方代码、CSP 和媒体生命周期。改为 HttpOnly Cookie 会引入 CSRF、过期和访客能力令牌兼容问题，不作为纯视觉修改悄悄迁移；如审查后选择迁移，以单独 ADR 和完整认证测试交付。

当前 localhost Compose 是 HTTP，不能把设备消息保护扩写成浏览器到后端全部加密。远程或局域网演示需要正确配置 TLS 和证书信任。安全页面显示真实部署事实，不显示虚构 HTTPS 勾选。

设备反馈驱动、活体抵抗、模型误识/误拒、设备更新完整性、密钥硬件保护、审计防篡改尚不能从软件界面推断已具备。列入未验收能力；必要时按任务书增加实验。

## 11. 工程结构方案

选择 Vue 3 + Vite + Router，后端继续 Flask 模块化应用；单站点 SQLite 和 Compose 保留。增加前端 TypeScript 约束，优先类型化 API、认证与命令状态，再迁移页面；完成后不得长期留两份行为不同的领域逻辑。

[Vue 官方 TypeScript 说明](https://vuejs.org/guide/typescript/overview.html) 明确区分 Vite 转译与类型检查。CI 单独加入 `vue-tsc --noEmit`，不能以生产构建成功代替类型检查。测试对外部 JSON 仍需做运行时边界验证，类型断言不是接口校验。

建议结构：

```text
src/
  app/                 应用启动、路由、布局、导航元数据
  shared/
    ui/                按钮、弹窗、标签、通知、空状态
    styles/            色彩、排版、间距、动效令牌
    api/               HTTP、错误映射、基础类型
    lib/               时间、格式化与可访问性辅助
  features/
    auth/              登录、TOTP、会话与改密
    home/              家门总览与设备选择
    door/              认证、命令与恢复状态
    camera/            受保护图像及元数据
    activity/          活动与审计表现
    guests/            邀请与公共访客流程
    administration/    审批、授权与报警
    security/          只读配置事实与验证报告
tests/
  unit/                领域转换、恢复与请求隔离
  browser/             真实用户流程和响应式验收
```

每个业务功能按必要性包含 API adapter、domain/types、model/composable、components 和 page；不为简单功能制造五层空文件。页面负责组合，API adapter 负责数据边界，领域负责规则和状态，UI 组件不自己请求业务 API。

`useDoorSession`、`commandStatus`、`guestFlow` 和 `usePrivateImage` 的有效行为迁移为领域功能。设备上下文和命令结果保持同一拥有者；保留请求代次隔离、图像 URL 回收、组件离开清理和重复提交保护。没有足够跨模块共享需求时不强行增加全局状态库。

新增接口必须有输入校验、服务端授权、稳定错误码、返回类型、迁移策略和接口测试。旧入口可以有明确的短期兼容，不能以别名或薄壳永久包住旧巨型页面。

## 12. 必要数据契约与迁移

| 需求 | 现状 | 拟定契约 | 迁移与限制 |
| --- | --- | --- | --- |
| 设备显示名 | 只有 ID，无显示名 | 可空 `display_name`，显示回退 ID；管理接口修改 | 授权用户可读，管理员改名，审计修改；不凭名称做授权 |
| 电量 | 模型有可空 `battery` | 仅有效且有真实来源时显示数值 | 不伪造百分比；设备是否采集需验证 |
| 时间 | 多个 naive 日期字符串 | 新 API 使用明确时区时间，保留来源 | 旧数据按已确认部署时区解释；未确认时不强行标 UTC |
| 快照时间 | API 只有路径，数据库有接收记录时间 | `received_at`；可信设备时间另用 `captured_at` | 两者不能混用；不补造旧拍摄时间 |
| 控制活动 | AccessLog 缺少设备、命令关联 | 新事件可含 device、command、actor、action、outcome、时间、来源 | 历史字段可空；不从名字或邻近时间猜关联 |
| 安全报告 | 测试代码与交付文档 | 脱敏、版本化报告 schema | 管理鉴权，仅只读；标识历史/当前源码是否匹配 |

业务结果与审计事件应在可用范围内事务性持久化；低层拒绝事件使用脱敏受控日志，不无限保存任意攻击载荷。命令状态、媒体鉴权和访客能力令牌契约要保持兼容，任何扩展先验证不会放宽原权限。

## 13. 演示环境与实物边界

三类环境明确区分：

1. **实际部署**：真实账号、设备、媒体、密钥与数据卷；保持限制，不注入演示数据。
2. **隔离演示**：独立 Compose 项目、端口、数据卷和密钥；可信模拟设备走真实协议与 API；页面明确标“演示设备/合成图像”。
3. **自动化测试**：临时数据库、固定合成数据与故障注入；用于回归和报告，不作为生产配置。

模拟设备证明软件业务和协议；实物设备才能证明摄像头、驱动和物理反馈。实物缺失时，以合成输入展示软件执行器，并明确未完成实物验收。不要把只播放前端动画叫做端到端开锁。

演示用例运行入口采用固定的测试场景，不要求把生产限制关掉；重放、篡改、过期、撤权与响应丢失测试只在隔离环境执行。报告保留测试失败，不能以永远全绿模板替代结果。

## 14. 实施顺序与阶段退出标准

在未获截止时间前，以阶段定义范围，不给未经验证的日历承诺。

| 阶段 | 具体工作 | 退出标准 |
| --- | --- | --- |
| A：需求与契约冻结 | 整理任务书、角色、P0/P1、威胁模型、API 缺口、设计 ADR | 每项必做有需求编号、负责人角色、验收方式；无虚假能力 |
| B：设计系统与完整视觉稿 | 登录、首页、手机、设置、管理证据；正常/空/离线/未知稿 | 确认温暖方向，信息层级、操作和状态可读 |
| C：结构与数据基础 | TS/API/领域模块迁移，显示名、时间、事件与报告契约 | 类型检查、接口和旧业务测试通过；迁移与回退说明完整 |
| D：关键垂直链路 | 登录→家门→画面→验证→原命令结果；响应丢失和离线分支 | 真实后端联调；正常与失败同样可用 |
| E：全页面完成 | 动态、访客、设置、审批、权限、报警、安全证据 | 角色隔离正确；手机/桌面/键盘流程完整 |
| F：安全与交付验收 | 固定隔离场景、报告、Docker、备份演练、答辩材料 | 报告匹配最终源码，服务可复建，限制可解释 |

不能只完成首页后宣布改版结束；所有现有业务入口与异常流程都在交付范围。不可为了赶页面隐去安全机制或删除失败分支。

## 15. 验收矩阵

| 维度 | 必查场景 | 通过条件 |
| --- | --- | --- |
| 身份与授权 | 未登录、未审批、无授权、撤权、TOTP 错误/过期 | 页面引导清楚，服务端拒绝不越权 |
| 开门执行 | 成功、失败、未知、过期、响应丢失、重复点击、并发 | 不假成功，不重复动作，原操作可恢复 |
| 媒体 | 有图、无图、切设备、延迟返回、离开页面、撤权 | 不显示别台陈旧图，不泄漏或残留受保护内容 |
| 访客 | 有效、无效、额度耗尽、撤销、消费响应丢失 | 额度含义准确，凭证生命周期正确 |
| 管理 | 审批、授权失败、未上报但已授权设备、报警处理失败 | 不吞掉已有授权，不显示虚假保存成功 |
| 视觉与可访问性 | 320/390/768/1280/1440 px，200% 文本，键盘/焦点/减少动效 | 无关键内容遮挡；文本、焦点和触摸目标可用 |
| 协议安全 | 篡改、重放、跨设备、并发、重启、过期会话 | 拒绝且不造成未授权状态改变；证据可复现 |
| 部署 | 空环境初始化、重启、深链接、静态资源/API、备份恢复 | 可复建，数据持久，报告对应源码 |

性能应在明确设备、网络与数据量下记录首次加载、画面读取和操作耗时。报告 median/p95 及失败率，分别列后台响应与硬件/协议等待；阈值在基线测量后冻结，不写未经测量的低延迟宣传。

安排 5–8 名同学开展小样本形成性试用，完成看状态、查看画面、邀请并撤销访客、处理超时四类任务。记录是否独立完成、误操作和理解问题；这不是可推广到真实家庭人群的统计结论。

## 16. 建议答辩顺序

按老师实际时限缩放，建议 8–10 分钟演示主体：

1. 说明家庭场景和系统边界，展示手机与桌面首页。
2. 正常登录、查看最近画面并完成一次安全开门软件链路；如有实物，显示真实反馈。
3. 创建访客、验证，再撤销，展示生命周期。
4. 在隔离环境展示越权、重放和篡改被拒的结果。
5. 注入响应丢失或设备不回执，说明原操作恢复和未知结果为何不会自动重发。
6. 展示架构、状态图、测试报告与 Docker 复建证据，说明尚未验收的硬件能力。

避免演示默认密码、个人脸图、密钥、认证器种子或生产访客凭证。验证截图标环境、源码版本、输入场景和结果。

## 17. 交付文件建议

需求与用例、页面与状态设计、架构/ER/时序/状态图、API 与错误码、威胁模型、安全用例与结果、ADR、部署和恢复说明、答辩脚本及短视频。

建立需求—设计—模块—用例—证据追踪矩阵。示例：`SEC-REPLAY-01` → 安全信封与持久化去重 → 协议/接收模块 → 并发重放与重启测试 → 对应版本报告。编号是拟定管理方式，不是已有测试 ID。

## 18. 对上一轮材料的更正

源码确认 `GuestPass.guest_name` 和可空 `Device.battery` 已存在；因此新版保留访客称呼，并对电量按实际数据决定是否显示。设备显示名、统一时间和完整控制事件关联仍需扩展。

此前对完整合并时间线、家庭成员叫法和快照时间较容易产生能力联想；本方案已明确：新元数据完成前保留分区与历史缺省值，账号不等于家庭关系，接收时间不等于拍摄时间。

最终实施选择：温润家居作为默认视觉，日常与管理证据分层，保持现有安全业务并完成必要数据扩展；以真实链路、可复现测试和完整工程资料支撑网络安全方向综合设计。

## 19. 旧版本与先进加密方案比较（根据用户补充深化）

### 19.1 实际版本调查

检查 Git 历史 `77fb55d` 之前的 ECC/AES 文件、上学期提交 `15ad3f5`，以及当前 v2 的封装、接收、会话存储、发送和命令代码。

| 层次 | 实际发现 | 评价与处理 |
| --- | --- | --- |
| 历史 AES-CBC | 固定 IV；`random.sample` 生成字符串密钥 | 不能作为新版本安全基线；在报告中说明改进，不重新启用 |
| 历史 ECC 包装 | P-256 ECDH + HKDF，派生材料与 AES key 异或；另有 Ed25519 签名辅助函数 | 辅助函数存在不代表全部业务报文已完成认证；不把自制包装称为成熟 ECIES |
| 上学期 v2 | python-spake2、HKDF、CBC + HMAC、nonce 和上下文 | 已有有价值的协议结构，应结合实现审查 |
| 当前 v2 | 随机 IV；分离加密/MAC 密钥；先验 MAC 再解密；设备/会话校验；数据库请求去重 | 保留作为可运行基线，继续验证上下文与生命周期 |
| 当前结果返回 | 命令同步响应有请求/端点绑定 MAC，并非所有响应都有同等应用层保护 | 完整 TLS 必须覆盖传输；升级时统一定义必要响应保护 |
| 当前执行层 | 一次性授权原子消费、短期命令、设备持久化执行记录和回执 | 密码算法之外的安全重点，升级协议不能删掉 |

历史缺陷仅描述已读到的代码，不表示当前运行 Docker 正在使用这些旧路径。当前正常设备通信走 v2；旧上传兼容由配置控制。

### 19.2 参考专业方案

| 方案 | 解决的问题 | 对当前项目的取舍 |
| --- | --- | --- |
| [TLS 1.3 / RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) | 标准传输保密、完整性与服务端认证 | 优先用于浏览器和设备到后端的真实远程访问；不关闭证书校验 |
| SPAKE2 / [RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html) | 共享口令参与的密钥协商 | 保留课程研究价值；审查身份、transcript 与密钥确认，不能直接等同库的 RFC 互操作性 |
| 现有 CBC + HMAC | 组合消息加密与认证 | 在正确组合和先验 MAC 下作为兼容基线，不能简单宣称 CBC 一定不安全 |
| AES-GCM | AEAD，统一加密及认证接口 | **选为 v3 消息封装主候选**，显式定义 AAD、nonce、分方向密钥和版本 |
| [ChaCha20-Poly1305 / RFC 8439](https://www.rfc-editor.org/rfc/rfc8439.html) | 另一种成熟 AEAD 构造 | 作为同环境基准对照；不凭硬件名称断言它一定更快，也不同时开放任意算法协商 |
| mTLS | 客户端证书身份和标准双向认证 | 专业化扩展有价值，但 CA、签发、轮换与撤销需完整交付；不只添加一个客户端证书文件就称具备 PKI |
| 自制 ECDH + hash/XOR | 自行拼装密钥/身份机制 | 不选；已有标准库和协议时不扩大自制密码面 |

[cryptography 的 AEAD 官方文档](https://cryptography.io/en/46.0.5/hazmat/primitives/aead/)强调同一密钥下不得重复 nonce。AEAD 不解决业务重放、越权、一次性消费、超时或反馈真实性；这些控制仍须独立保留。

重要库限制：[python-spake2 官方安全说明](https://github.com/warner/python-spake2#security)明确指出其实现不是常量时间、不能防御计时攻击。限流和 TLS 可以减少部分暴露，但不能把该实现变成常量时间，也不能据此获得完整侧信道安全保证。课程报告必须记录这一限制；真正产品化需选择适合的成熟实现或标准设备认证方案并重新验证。

### 19.3 确定的升级路线

1. 先完成现有 v2 的安全回归与协议 ADR，封住旧协议降级；远程演示启用正确 TLS，保护登录、影像、状态和设备通信。
2. 将密码协议模块与业务模块分开，协议定义与测试向量统一，避免设备端和后端复制后逐渐不一致。
3. 独立实现 `SL-SEC-v3` AEAD profile，默认 AES-GCM；v2 保持明确短期兼容，不静默降级。v3 是计划，不是当前已实现。
4. AAD 绑定版本、设备、会话、请求、时间、方法、端点、方向等上下文；设备身份来自认证上下文，不能由明文字段自由选择。
5. 明确定义确认交换与握手 transcript、双方身份、期限和版本的绑定；双方确认完成前不把会话标为完整激活。不在方案阶段凭摘要宣称已证明协议安全。
6. HKDF 做方向/用途分离。nonce 唯一性有独立设计与测试：若采用计数器，必须持久化/原子分配，重启或不确定写入时更换会话密钥；不能直接从两个线程各自从零计数。若使用随机 nonce，必须限制每密钥消息量并量化碰撞边界。
7. 认证失败不提供业务明文和不同 padding 细节；应用层拒绝不触发重签发或动作重试。TLS 身份与消息身份要有明确映射。
8. 在 Pi 4B 上测 CBC+HMAC、AES-GCM、ChaCha20-Poly1305 的握手、控制报文、JPEG 封装开销，记录库、OpenSSL、架构和输入大小。AES-GCM 为设计默认；若同环境数据证明不适合，按 ADR 改选，不能静默改变协议。
9. v3 通过跨端、篡改、重放、并发、重启、错误方向/端点、未知版本与降级测试后，才切换设备和后端默认版本。

这是独立安全工作包，不能和页面配色一起未经协议评审就上线。网络安全方向成果应包含旧/新方案比较、设计理由和测试结果；不要只列算法名。

## 20. Raspberry Pi 4B / 2 GB 的部署与资源方案

[官方规格](https://www.raspberrypi.com/products/raspberry-pi-4-model-b/specifications/)确认 Pi 4B 提供 2 GB 型号。资源方案以用户拥有的这一型号为目标，所有耗时、内存与温度结论必须由该板实际测量。

**默认选择：Pi 运行设备软件，后端和网页部署在现有电脑 Docker。** 浏览器在手机/电脑渲染；Pi 不运行 Vite、不在板上编译大型视觉依赖，也不运行用于展示的浏览器。

```text
手机 / 电脑浏览器
       │ HTTPS
电脑 Docker：Web 入口 + Flask + 数据库 + 媒体 + 通知
       │ HTTPS + 明确设备认证 / 消息保护
Pi 4B 2 GB：采集 + 人脸推理 + 心跳 + 命令执行/反馈
       │
摄像头、锁执行驱动、可信反馈（需实物接入）
```

理由：将有限板内存留给采集、模型与执行；两端边界也更适合展示安全通信。局域网演示要给 Pi 配置电脑可达地址，不能把 `localhost` 当成另一台主机；证书必须匹配该地址/名称。若没有独立后端主机，再制定共机配置与单独容量验收，不能直接照搬默认双 worker 后端。

设备侧确定原则：

- 64 位运行环境；优先在构建主机交付 linux/arm64 镜像，再在板上验证，不拿 Windows/x86 构建结果替代 ARM 结果。
- 一个设备 worker，模型单份加载，控制线程与摄像头操作解耦；摄像头采集串行，控制队列有边界。
- 已有 640×480 Picamera2 采集可作为初始配置；USB 路径也应明确采集分辨率和 JPEG 上限。最终参数按识别质量与板上资源测量确定。
- 只在需要验证或查看时采集/传输画面，不为了页面生动持续上传高分辨率帧；前端不自动高频刷新。
- 现有设备容器 `mem_limit: 1200m` 是保护上限，不是测得的占用；不要默认加大。记录 RSS、容器内存、OOM、CPU、温度、降频、存储增长与请求失败率。
- 单独记录人脸推理与密码握手/封装开销，避免将视觉等待误判成加密性能问题。握手复用到会话期限，而非每帧重复协商。
- 线程限制继续控制 OpenBLAS/OMP；图像队列有界，日志滚动，状态库保留防重复执行证据。
- 当前 Compose 映射 `/dev/video0`，不能据此认定 CSI 已可用。用户摄像头型号确认后，分别处理 V4L2 或 libcamera/Picamera2 与权限。
- 当前生产入口采用 `UnavailableActuator`，并未安装实物驱动；实体开锁须接入执行与传感反馈，不允许将继电器写入成功等同门锁已打开。

板上验收包括：冷启动与模型加载、连续认证、控制与采集并发、断网恢复、设备重启、重复命令、摄像头故障、驱动反馈不符、持续运行资源曲线。持续测试长度按实际可用时间定义并记录，不能把短时测试叫长期稳定性验证。

## 21. 根据用户补充调整的阶段关系

前端家居体验重构与协议审查可以分别推进；协议 v3 单独交付和切换。安全审查若发现直接影响权限、重放或动作执行的真实缺陷，先修复该缺陷，再扩大视觉与协议改动。

最终建议顺序：真实业务和 v2 基线验证 → 完整暖色视觉与结构重构 → 必要数据契约/只读证据 → TLS 与 Pi 实机链路 → 独立 v3 AEAD 验证/迁移 → 整体演示与交付报告。每阶段用验收条件完成，不以工作量大小替代结果。

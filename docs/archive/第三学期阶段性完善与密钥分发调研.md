# 智能摄像头门锁：第三学期阶段性完善与密钥分发调研

## 1. 本阶段定位

项目已经完成“账号/MFA、人脸识别、树莓派设备、开门令牌、前后端联调”等主体功能。本学期不再扩展大量业务功能，而是围绕老师指定的**密钥分发**问题，把设备接入和开门通信从“能用”提升到“密钥可配置、可轮换、可撤销、可验证”。

本阶段目标：

1. 明确设备、后端、用户三类主体的密钥和信任关系，形成一张协议时序图。
2. 为每台设备建立独立的设备凭据，取消生产环境依赖统一默认口令。
3. 增加设备密钥轮换/吊销的最小闭环，并将会话状态和重放保护从单纯进程内存改为可持久化设计（演示版可先落 SQLite）。
4. 完成自动化测试和攻击场景演示：重放、篡改、过期会话、错误设备身份均应失败。
5. 输出可放入 PPT 的实验数据和风险对比，不追求大规模重构。

## 2. 现有系统结构与安全实现

### 2.1 代码对应关系

| 模块     | 当前实现                                              | 与密钥分发的关系                                                |
| ------ | ------------------------------------------------- | ------------------------------------------------------- |
| 树莓派发送端 | `paspberry_pi/transmit.py`                        | 读取设备 ID/口令；调用 SPAKE2；封装安全包；仍保留旧版回退                      |
| 协议实现   | `paspberry_pi/security_protocol.py`、后端同名文件        | SPAKE2-A/B、HKDF、AES-CBC、HMAC、nonce、request_id、timestamp |
| 后端握手   | `BE_smart_lock/smart_lock/app/routes/security.py` | `/api/security/spake2/start`；按 device_id 获取口令；生成短期会话    |
| 后端解包   | `.../routes/secure_payload.py`                    | 校验会话、设备、时间、MAC，维护重放集合；兼容旧 ECC+AES                       |
| 设备绑定   | `.../routes/mfa.py`、`models.py`                   | `MFACredential` 保存设备绑定和公钥字段；`Device` 保存在线状态             |
| 长期密钥   | `backend_priv.pem`、`backend_pub.pem`              | 旧版 ECC 包装 AES key 使用；私钥当前以文件形式加载                        |
| 开门授权   | `AuthSession`、`UnlockToken`                       | 多因子认证后签发一次性、有时效的开门令牌                                    |

### 2.2 当前 v2 数据流

```text
设备                         后端
  |-- device_id, SPAKE2_A, client_nonce -->|
  |<-- SPAKE2_B, server_nonce, challenge ---|
  |       双方计算 spake2_key                |
  |       HKDF(spake2_key, nonce, device_id)
  |       = session_key                      |
  |-- AES-CBC(ciphertext) + HMAC + nonce --->|
  |<-- 校验后执行业务/开门令牌流程 -----------|
```

这套设计已经具备“通过口令认证后动态分发短期会话密钥”的雏形：口令本身不在网络上传输，业务数据不直接使用长期设备口令，且会话有 300 秒有效期。

## 3. 密钥分发调研结论

### 3.1 为什么不能只说“用了 AES”

智能门锁的核心问题不是选哪种加密算法，而是：**谁拥有密钥、密钥如何首次进入设备、如何证明对端身份、泄露后如何止损、设备离线时如何撤销**。因此应把密钥生命周期拆成：生成、注册/入网、分发、使用、轮换、吊销、销毁、审计。

### 3.2 三种常见方案比较

| 方案                               | 优点                      | 主要问题              | 本项目取舍                           |
| -------------------------------- | ----------------------- | ----------------- | ------------------------------- |
| 预置共享口令 + PAKE（SPAKE2）            | 适合资源受限设备；不直接传口令；可派生会话密钥 | 需要安全注入口令；口令泄露需轮换  | 作为当前 v2 的近期方案                   |
| 非对称设备身份（Ed25519/ECDSA 签名 + ECDH） | 设备可独立身份认证；便于吊销和审计       | 首次注册/证书或公钥信任链更复杂  | 作为后续增强方向；本阶段先保存设备公钥指纹           |
| TLS/DTLS + 服务端证书或 mTLS           | 标准化程度高，工程生态成熟           | 证书签发、更新、离线策略有运维成本 | 传输层应使用 HTTPS；应用层 v2 作为课程演示的额外保护 |

推荐结论：短期保留 SPAKE2 作为设备入网/会话建立机制；为每台设备配置独立高熵凭据并支持轮换；在设备注册时记录公钥指纹和状态；生产化时迁移到 TLS 1.3 + 设备证书/mTLS。

### 3.3 本项目现状中的关键风险

1. `get_device_password()` 在没有设备专属配置时回退到统一默认口令，导致一台设备泄露可能影响所有设备。
2. `SECURITY_SESSIONS`、`SEEN_REQUEST_IDS`、`SEEN_NONCES` 为进程内对象，重启或多进程部署后会丢失状态。
3. 旧版 `ECCalgorithm.py` 使用 ECDH 派生值与 AES key 做 XOR，且旧 AES-CBC 使用固定 IV；应限制为迁移兼容，不应作为新设备默认路径。
4. `backend_priv.pem` 以未加密 PEM 文件加载，文件权限、备份和轮换策略尚未形成文档化闭环。
5. `paspberry_pi/transmit.py` 在 v2 异常时自动回退旧版，若生产环境仍开启，可能形成降级攻击面。
6. 设备绑定接口中的 `device_pubkey` 已有字段，但当前并未形成完整的公钥校验和吊销流程。

## 4. 实施计划（后续的阶段性计划）

### 第 1 周：模型、协议和密钥管理闭环

**第 1-2 天：密钥资产盘点与协议图**

- 建立 `docs/key-management.md`，记录每类密钥的持有者、用途、有效期和备份要求。
- 在 PPT 中画出“设备首次注册→SPAKE2 握手→会话密钥→开门令牌”的时序图。
- 为 `device_id` 增加唯一设备凭据配置约定，明确禁止默认口令进入生产配置。

**第 3-4 天：设备凭据与轮换接口**

- 在 `Device` 或独立 `DeviceCredential` 表增加：`credential_version`、`secret_hash`/加密存储值、`status(active/revoked)`、`rotated_at`、`last_seen`。
- 增加管理员接口：生成新设备凭据、激活、吊销、轮换；接口只返回一次明文凭据，并记录审计日志。
- `get_device_password(device_id)` 改为优先读取设备专属凭据；默认值仅允许开发环境使用并启动时给出警告。

**第 5 天：会话和重放状态持久化**

- 阶段版将会话元数据和已用 `request_id/nonce` 落 SQLite；至少保存哈希、设备 ID、过期时间。
- 保留内存缓存作为性能优化，但重启后不能接受已失效或重复请求。

### 第 2 周：安全强化、测试和展示材料

**第 6-7 天：关闭不必要的降级路径**

- 增加配置项 `ALLOW_LEGACY_SECURITY=false`，生产/演示默认关闭旧 ECC+AES 回退。
- 新设备只允许 v2 安全包；兼容旧设备时单独开启并在日志中标记。
- 新增服务端启动检查：检查 `JWT_SECRET_KEY`、设备专属凭据、私钥文件权限和 HTTPS 配置。

**第 8-9 天：密钥轮换与失效测试**

- 测试轮换前会话在策略允许/不允许时的行为，明确“旧会话最多存活多久”。
- 测试吊销设备后：握手失败、旧 session 失效、旧 unlock token 不能开门。
- 测试错误设备 ID、篡改 ciphertext/MAC、重复 request_id、过期 timestamp。

**第 10 天：实验数据和 PPT**

- 记录 20 次正常握手的成功率、平均耗时；记录 5 类攻击各 5 次的拦截率。
- 准备一段演示：正常开门成功→抓取并重放旧包失败→轮换凭据→旧设备再次失败。
- 更新 README/API 文档，补充配置示例和密钥生命周期图。

## 5. 验收标准

| 验收项  | 最低标准                                   |
| ---- | -------------------------------------- |
| 设备隔离 | `door_01` 的凭据不能完成 `door_02` 握手         |
| 密钥轮换 | 管理员轮换后新凭据成功，旧凭据失败                      |
| 吊销   | 吊销设备后新握手和旧会话业务请求均失败                    |
| 防重放  | 同一 request_id 或 nonce 第二次请求返回 4xx，并有日志 |
| 防篡改  | 修改 ciphertext、header 或 MAC 均无法解密       |
| 时效性  | 超过允许时钟偏差的包被拒绝                          |
| 降级控制 | `ALLOW_LEGACY_SECURITY=false` 时旧格式被拒绝  |
| 可演示性 | 能展示正常链路和至少三种攻击失败结果                     |

## 6. PPT 建议结构（8 页）

1. 项目现状：摄像头、人脸识别、MFA、树莓派、后端和前端。
2. 本学期问题：门锁系统中的密钥分发与生命周期。
3. 威胁模型：窃听、重放、中间人、设备克隆、服务器泄露、降级攻击。
4. 当前 v2 协议：SPAKE2 + HKDF + AES-CBC/HMAC 时序图。
5. 代码映射：`security.py`、`security_protocol.py`、`secure_payload.py`、`transmit.py`。
6. 现状不足：默认设备口令、内存会话、旧版回退、密钥轮换缺失。
7. 两周改进方案：设备凭据表、轮换/吊销、持久化重放保护、测试矩阵。
8. 阶段成果与下一步：指标、演示、后续 TLS 1.3/mTLS 方向。

## 8. 汇报时需要主动说明的边界

当前项目是课程原型，不应表述为“已经达到商用门锁安全等级”。本阶段的目标是把密钥分发问题具体化、可验证化：明确设备独立身份，完成会话密钥建立、轮换和吊销的最小闭环，并用可重复实验说明防重放和防篡改效果。真正生产化还需要硬件安全模块/安全芯片、TLS 证书运维、固件签名与安全启动、数据库和备份系统的密钥保护等工作。

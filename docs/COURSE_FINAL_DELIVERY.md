## 使用与现场准备

1. 电脑和 Pi 处于相互可达的网络，Pi 主机名 smartlock、Linux 用户 taylor。IP 改变时重新确认地址和 SSH 主机密钥，不跳过校验。
2. Docker Desktop 运行，执行 `docker compose -f compose.yaml -f compose.tls.yaml up -d --wait`。
3. 保持 `deploy/pi_tunnel.py` 运行，具体参数见部署手册。当前实验使用双向 loopback 转发，电脑关闭或换网会中断设备通信。
4. Pi 检查 `systemctl --user is-active smart-lock-device`。不要把根路径 200 当作人脸就绪；空模板应返回 503。
5. 打开 http://localhost:8080/，使用 taylor 的独立项目密码；首次绑定 TOTP 后登录。账号授权和设备认证绑定是不同步骤。
6. 选择 pi_csi_01，确认设备在线、摄像头在线、锁上报 UNKNOWN。网页拍摄只显示新照片确认成功；刷新只读取已存媒体。
7. 摄像头固定在稳定位置，避免手持晃动、手指遮挡和排线拉扯。改变排线连接前关机断电。

不提供默认密码，不把树莓派登录密码用于项目账号或设备口令。答辩投屏时隐藏 TOTP 种子、二维码、访问令牌、访客凭证和私钥。个人脸图不进入公开提交材料。

## 本人脸登记与评测流程

登记需要本人明确同意，确认账号为 taylor。设备上保留用于识别的 128 维模板；源图、模板和测试证据放在忽略目录。拒绝多脸、无脸、重复图或无效向量。

1. 在稳定光照下采集至少 3 张不同照片：正面、稍向左、稍向右。保持适当距离，保证只有本人进入画面。不要用同一张图片复制成多张。
2. 使用原生 `.venv-pi/bin/python paspberry_pi/manage_templates.py`，指定现有 `deploy/device/templates` 目录执行 enroll，再执行 validate/list。命令详见部署手册。已有模板必须显式替换。
3. 在维护窗口重启设备服务，核对配置就绪 200；就绪只代表模型和模板有效。
4. 本人登录并绑定设备，点击“验证并开门”。记录识别结果、必要 TOTP、授权受理与执行结果。没有锁具时最终执行应失败，不能伪装确认。
5. 至少进行同光照、不同距离和侧脸的独立试次，记录接受/拒绝、耗时和条件。使用其他人的人脸必须获得本人同意；没有负样本则不得报告误识率。
6. 无脸、多脸、超时、错误 TOTP、过期、撤权、重复消息必须拒绝或明确失败。照片/屏幕攻击可在受控实验中记录系统限制，不把 TOTP 当成活体算法。

评测表：试次编号、时间、设备与版本、样本条件、预期身份、系统结果、采集/推理/总延时、失败原因。小样本通过率只是这批实验的描述，不能推广成商业准确率。

## 常见答辩问题

**为什么既有 HTTPS，又有设备消息加密？** HTTPS 保护传输及服务器身份；设备协议使用独立设备凭据、双向密钥确认和认证信封，绑定设备、端点与消息生命周期。它不消除服务器信任，也不意味着图像对后端不可见。

**为什么采用 SPAKE2 和 AES-GCM？** 以独立设备秘密建立会话并确认双方密钥，使用 AEAD 同时保护内容及关联数据。实现复用集中协议包，禁止遇到错误自动降级。具体设计与限制见架构、协议文档和测试。

**为什么不能收到 HTTP 200 就显示开门成功？** 令牌受理、指令创建、设备执行和传感器反馈属于不同阶段。只有实际执行回执和可信反馈满足条件才确认动作；没有硬件就显示 UNKNOWN/失败。

**能防照片攻击吗？** 当前没有 PAD 算法，不能宣称能防。TOTP 提高认证强度但不验证照片来源。此限制必须保留在需求、测试和结论中。

**树莓派 2GB 能否稳定运行？** 已有实机采集与设备服务验证；长时负载、识别性能和整机恢复需要对应实验，不能由一次启动推导长期可靠性。

**为什么不用微服务或全部运行在 Pi？** 当前单家庭课程规模适合模块化单体；工作站承担网页和业务，Pi 负责采集与设备执行。降低部署和资源复杂度，保持明确的信任边界。

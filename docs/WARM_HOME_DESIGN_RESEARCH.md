# 智能家居门锁与摄像头：温暖体验调研及设计修订

调研日期：2026-10-08。状态：设计建议，尚未实施。本轮仅新增调研文档，不修改应用代码、运行中的 Docker 服务或业务数据。

## 1. 定位修正

产品服务于家庭日常：看看门前、确认门锁、让受邀的人进门、了解刚才发生的事情。此前方案把“工业化”主要表达成了企业管理台的视觉语言，代码结构有价值，但界面的情绪与使用场景偏离了家居定位。

新版目标是：温暖、安静、亲切、状态可信、操作清楚。工程结构继续采用明确的领域状态、共享组件、语义令牌和完整异常处理；视觉上突出家庭生活。

“温暖”须落实到信息顺序、空间感、触摸体验、生活语言、引导和状态反馈。只把蓝色换成橙色不足以达到目标。

## 2. 调研方法与证据边界

覆盖 12 个品牌或生态：Apple Home、Google Home/Nest、Aqara、Yale、eufy、Ring、Nuki、Tapo、米家、IKEA Home smart、Samsung SmartThings、Home Assistant。另查阅 Google 官方设计访谈、自然材质设计文章和 W3C 可访问性规范。

优先采用官方产品页、支持文档、设计团队访谈。区分三类内容：

- **已核实事实**：官方页面明确描述的组织方式、功能和交互。
- **设计推论**：从事实提炼的、适合本项目的设计建议。
- **本项目约束**：依据仓库接口和代码确定的现有能力。

没有把这些品牌的全部功能视为本项目已有能力，也没有进行每个 App 的登录后实机体验。官方页面可能展示不同地区、不同版本和营销示意；不能据此推断所有当前版本的具体像素、颜色或操作路径。本轮提出的颜色是原创方案，不是从竞品精确取色。

Yale 官方 PDF 文本可读取，但截图工具的重定向检查阻止了页面截图；不把它当作已经完成的视觉逐页验证。小米以可访问的官方产品页为证据，不以旧款宣传页推断新款 App 全貌。

## 4. 当前界面为什么显冷

依据当前 `tokens.css`、`AppLayout.vue`、`DoorsView.vue` 和页面结构：

1. 深石墨侧栏与高饱和蓝主按钮占据主要品牌印象，接近企业 SaaS 管理台。
2. “ACCESS MANAGEMENT”“工作空间”“门控”“已上报设备”等语言强调管理系统身份。
3. 首屏先显示设备总数、在线数和离线数，对只有一扇门的家庭价值有限。
4. 设备 ID、表格、服务器时间与身份验证说明过于靠前，用户需要自行翻译成家庭场景。
5. 摄像头画面和锁操作没有形成强烈的整体家门体验。
6. 空状态偏向交代系统前置条件，缺少帮助用户完成下一步的具体指引。

这些是本项目界面审查判断，不是已开展用户测试后的统计结论。

## 5. 三个候选方向

| 方向 | 表现 | 适用性 | 判断 |
| --- | --- | --- | --- |
| A：温润家居 | 燕麦白、暖灰、深陶土色主动作、少量柔和绿；浅色导航和留白 | 门锁摄像头、日常使用、手机和桌面均可保持清楚 | **推荐**：有温度且稳重 |
| B：明亮亲和 | 偏白背景、柔和杏色、圆润图标、较活泼的插画 | 轻量家庭设备、偏年轻用户 | 可作对照稿；注意杏色按钮对比和卡通化 |
| C：安静夜间 | 深暖灰、琥珀小面积点缀、克制的暗色卡片 | 夜间查看门口 | 适合作为后续夜间主题，不作为首轮默认主题 |

选择 A 的原因：温度从整体空间、语言与组织方式共同产生，避免所有功能都挤在暖色块里；深陶土色提供稳定的按钮对比，绿、黄、红继续承担状态含义。

## 6. 视觉系统建议

以下为初稿令牌，需在真实画面与异常页面中复审：

| 角色 | 初稿色值 | 用法 |
| --- | --- | --- |
| 页面背景 | `#F7F3EC` | 燕麦白，整个应用的温度基础 |
| 卡片背景 | `#FFFCF7` | 近白而略暖，保持画面和文字清楚 |
| 主要文字 | `#302D28` | 深暖灰，避免大量纯黑 |
| 次要文字 | `#716A61` | 温灰，仍能支撑正文阅读 |
| 主动作 | `#985638` | 深陶土色，用于明确的主要按钮与少量导航强调 |
| 柔和衬底 | `#EFE4D7` | 选中区域、引导卡；不是弱对比正文颜色 |
| 正常状态 | `#356B54` | 仅用于有证据的正常或成功状态 |
| 待确认/提醒 | `#886014` | 黄色系文字与图标，独立于品牌陶土色 |
| 危险/失败 | `#B33E3B` | 失败、真实告警和危险操作 |

本地按 WCAG 相对亮度公式计算：主要文字、次要文字、主动作文字、正常、提醒和危险色在卡片背景上的对比分别约为 13.40、5.21、5.51、6.07、5.50、5.59；白字在主动作色上约为 5.64。这里只验证这些静态色对，不代表全部控件和状态已满足可访问性。

普通正文至少 4.5:1、大号文字至少 3:1，依据 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)。卡片边界、焦点、图标和真实叠图须单独验收。默认主要触摸目标设计为至少 44×44 CSS px，这是本方案的产品目标；[WCAG 2.2 AA 的 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)采用 24×24 CSS px 或满足规定间距及例外，不能混淆。

形态与排版：

- 大卡片圆角 20–24 px，小控件 10–14 px；主动作保留容易识别的按钮形态。
- 阴影轻且带暖灰色，卡片层级主要由位置、间距和标题建立。
- 正文优先 16 px，辅助文字至少 13–14 px，中文保持舒适行距；代码式字体仅用于次级技术详情。
- 桌面标题 28–32 px，手机 24–28 px；采用系统中文字体，不强制新增远程字体依赖。
- 家门与摄像头图标保持统一笔画、稍柔和的转角；不混用 emoji 与图标库。
- 登录、初次设置和空状态可使用原创的玄关线条插画，面积克制。
- 真实摄像头画面不加暖色滤镜；无画面时用明确占位，不用漂亮的虚构门口冒充采集图像。
- 不用大面积毛玻璃、木纹、装饰性渐变或无限呼吸动画遮蔽家庭内容。

## 7. 信息架构与页面修订

### 7.1 导航

手机底部：我的家、动态、访客、设置。桌面采用对应的浅色窄侧栏或顶部导航，保持名称一致。后台审批与账号授权放在管理设置；真正需要关注的告警在首页和动态保持显著入口。

暂时保留当前路由和权限机制，由导航元数据映射名称；不为了外观迁移破坏深链接。普通用户不显示无权限的报警接口内容，也不加入一个全部为零的告警入口。

“我的家”是产品入口名称，当前仍是单站点、设备授权模型，不代表已实现多家庭、成员关系或租户隔离。

### 7.2 首页：我的家

首屏顺序建议：

1. 简短欢迎与当前选中设备；欢迎语不包含未经证实的“家里一切安全”。
2. 需要关注的异常提示；故障或锁状态未知时紧邻主要内容，不能沉到设置里。
3. 家门主区域：最近门前画面 + 门锁状态 + 最近上报 + 主要操作。
4. 快捷入口：邀请访客、查看最近动态、设备设置。
5. 最近动态预览；多设备家庭再出现设备卡片选择。

桌面采用画面与门锁控制的并列布局，手机顺序堆叠；两者属于同一设备上下文。操作按钮和验证步骤保持连续，不跳到另一套控制台。

把设备计数移到设备列表或设置。只有一台设备时，不显示“1 在线 / 0 离线”三块统计卡。多设备界面使用小卡片；只有 ID 的设备保持原 ID，不将其擅自命名为“入户门”。

### 7.3 门锁控制

主区域显示“最近上报：已锁 / 已解锁 / 状态未知”。连接在线与锁状态分别显示，不能用在线绿点暗示门已锁。

开门动作包含确认设备、必要身份验证、提交、等待回执、结果五个用户可理解阶段。技术授权令牌、消费恢复等仍由现有领域模块维护；页面用短提示解释下一步。

按钮以“验证并开门”“上锁”表达动作；绿色成功状态依据结果或设备反馈使用。验证通过、命令已提交、设备执行成功、最近物理锁状态是四类不同证据。

结果未知文案：“暂时没有收到执行结果，请先确认门锁状态。”保留现场核查与结束跟踪，不自动重发动作。不用“应该已开门”“再试一次即可”等模糊安慰。

### 7.4 摄像头

当前明确显示“最近画面”。提供获取画面、查看大图、删除相关受保护快照等现有操作。请求中、无记录、无权限、设备离线和获取失败分别表达。

当前 `/api/video/latest` 返回快照路径，不返回采集时间；因此不能把请求时间写成拍摄时间。旧 `/video_feed` 返回 410，不能放置 LIVE、直播绿点、录像拖动时间轴、对讲按钮或播放中的假状态。

未来真要做实时观看，须另立后端和设备端音视频协议、会话权限、时间元数据与隐私生命周期的需求。

### 7.5 动态

普通使用入口改为按日期分组的事件卡片；用户可以筛选设备与事件类型。管理员另可进入完整审计表。

有记录中的快照才显示缩略图；无快照不捏造场景。原动作码保留在详情，以便排查。时间没有时区信息时不擅自变换浏览器时区或生成“刚刚”；应先建立统一时间契约。

“开门命令已提交”不能改成“你回家了”。只有可靠的人物与行为数据才允许写关系式叙述。

### 7.6 访客

邀请流程强调目标设备、来访者标识、有效期与次数、分享、撤销。列表采用易读卡片，并显著标记已撤销、次数用尽等状态。

额度按当前接口真实定义呈现，不能把“验证次数”美化为“可开门次数”。现有接口没有访客姓名等字段时，不让新增表单输入后静默丢失。

访客验证页采用独立、简单的欢迎与步骤提示，保留验证失败、凭证失效、等待执行等完整状态；不显示家庭隐私内容。

### 7.7 用户与权限

入口可称“账号与访问权限”，保留管理员身份提示和设备权限表。暂不直接称“家庭成员”：数据库只有账号角色、审批状态和设备授权，尚无家庭成员关系。

未来建立家庭模型后，才能准确组织家人、访客和管理员；不能靠前端文案赋予权限关系。

### 7.8 登录、账户与首次设置

登录视觉采用浅暖背景、小幅玄关插画、清楚的登录表单，标题可为“欢迎回来”。注册文案解释审批机制，避免承诺注册后立即可用。

首次绑定认证器用 1–2–3 步骤，解释如何扫码、如何填验证码和如何处理绑定失败。密码、认证器与绑定设备分别组织，隐藏状态和失败原因不能被装饰吞没。

无设备时给出可执行的引导：账号是否审批通过、是否获得设备授权、是否完成绑定、设备是否已上报；依据真实状态显示步骤。设备凭据登记仍属运维命令，不虚构可点击的网页设备配对。

## 8. 文案样例

| 当前表达 | 建议表达 | 条件 |
| --- | --- | --- |
| 工作空间 | 我的家 | 作为入口名称，不作为多家庭模型声明 |
| ACCESS MANAGEMENT | 家门与门前画面 | 品牌副标题 |
| 门控 | 我的家 / 门锁 | 按页面层级使用 |
| 已上报设备 | 已连接的设备 | 列表仍需区分连接状态；技术详情保留上报字段 |
| 摄像头快照 | 最近画面 | 明确非实时且无可信采集时间 |
| 用户与权限 | 账号与访问权限 | 不捏造家庭关系 |
| 认证失败 | 本次验证未通过，请重新开始 | 保留可操作下一步与真实原因 |
| 执行回执描述本次操作 | 正在确认这次操作的结果 | 准确对应阶段，详情可保留技术解释 |
| UNKNOWN | 状态暂未确认 | 状态含义保持未知，不柔化为正常 |

温暖语言应短、自然、尊重用户。避免“主人”“小管家”“我正在守护你”等拟人化承诺，也不把错误说成可爱的小插曲。

## 9. 工程结构与实施切分

现有 Vue 3、Vite、Router、Axios 与领域状态模块可继续使用。修订重点是表现层与信息架构，先审查必要数据契约再决定后端扩展。

建议新增或调整：

- 语义令牌：页面、卡片、导航、主要动作、文字、边界、成功、待确认、危险；不能在各页散写色值。
- 应用壳：桌面导航、手机底部导航、设置分组和固定操作区域的安全间距。
- 领域表现组件：家门区域、门锁状态、最近画面、事件卡片、邀请卡片、配置步骤。
- 文案映射：真实动作与状态到用户语言的集中转换，原始状态保持可追溯。
- 响应式策略：窄屏以主要任务排序，宽屏并列画面与门锁；不简单把整个桌面表格缩小。

继续保护 `useDoorSession`、`guestFlow`、`commandStatus`、受保护图像的请求代次及回收机制。视觉交互不得绕过认证、重复提交防护或未知结果恢复。

能力切分：

| 类别 | 内容 | 下一步 |
| --- | --- | --- |
| 现有能力可完成 | 主题、布局、导航标签、门锁与画面组合、验证步骤、卡片式动态、访客表现、空状态 | 在现有 API 上实施 |
| 小范围完整扩展 | 设备显示名称、统一时间及快照采集时间 | 定义权限、字段迁移、接口、校验与回退后再实施 |
| 产品级新增 | 家庭/房间/成员模型、音视频直播与通话、设备电量、自动化场景 | 单独定义需求和设备能力，不作为当前主题改版附赠功能 |

设备显示名若实施必须在后端持久化并鉴权；不能用浏览器本地昵称假装所有家人共享的设备名称。统一时间接口需用明确时区的时间表达并保留原事件排序。

## 10. 审查问题与验收标准

设计审查先回答：

1. 在只有一台门锁的家庭，用户进入首屏能否直接找到画面、状态和操作？
2. 锁状态未知、设备离线时，温暖视觉是否仍让异常一眼可见？
3. 摄像头无画面时，整体是否仍像成熟家居产品，而不是破碎仪表盘？
4. 管理员配置是否从日常流程中合理后移，同时保持可发现？
5. 手机页面能否完成首次认证和开门，而不用理解专业术语？

实施验收：

- 同一组数据在桌面与手机上语义一致；检查 320、390、768、1280、1440 px 与 200% 文本放大。
- 检查正常、空设备、请求失败、离线、未知锁状态、验证失败、执行成功、执行失败与结果未知等页面。
- 主动作至少 44 px 触摸目标；焦点明确、键盘可用、弹窗焦点正确返回；底部导航不挡按钮。
- 状态同时使用文字、图标与必要颜色；正文对比验证到真实组件，不只检查颜色表。
- 继续运行现有单元测试、浏览器验收和真实后端联调；增加测试仅验证因本轮改版产生的新风险。
- 试用观察任务：确认门锁状态、查看最近画面、创建并撤销访客、从操作超时中恢复。记录是否能独立完成，而非仅问“好不好看”。
- Docker 重建后校验完整页面、静态资源、API 代理与健康状态；实际没有设备时准确说明能力空缺。

## 11. 推荐推进顺序

先制作 A/B 两套首页与登录视觉对照，并展示手机首页；同时呈现正常、无设备、离线、结果未知四种状态。确认方向后再批量实施所有页面。

视觉稿中如果需要模拟设备或门前画面，明确标注演示内容，和 Docker 的真实数据分开。首轮优先 A：温润家居，B 作为明亮亲和对照。

本轮结论：将产品从管理台式信息组织转向家门日常体验。保留工程结构与状态真实性，重做应用壳、首页、主要组件和文案；仅换主题色达不到预期。
